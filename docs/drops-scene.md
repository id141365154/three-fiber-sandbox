# Капли на воде: переход между картинками на React Three Fiber и GLSL

Знаете эффект, когда вы кликаете по картинке, из точки клика расходится неровное кольцо с лёгким «преломлением» на фронте, и внутри кольца проявляется следующая картинка? Выглядит как капля, упавшая на стекло. Так же красиво работает и при серии кликов: переходы накладываются друг на друга, как круги на воде.

В этой статье мы по шагам соберём такую сцену с нуля: от пустого `Canvas` до пяти-шести одновременных переходов с шумным краем, волной и бликом. По пути разберём приёмы, которые пригодятся в любых шейдерных эффектах: коррекцию пропорций, мягкие края через `smoothstep`, value noise, передачу массивов в uniform и генерацию GLSL-кода из JavaScript.

**Стек:** React, `@react-three/fiber`, `@react-three/drei`, `three`, `leva` для панели настроек. GLSL будем объяснять с нуля, так что знать шейдеры заранее не нужно. Достаточно уверенно читать React и иметь представление о том, что такое сцена, камера и меш в Three.js.

Исходники сцены лежат в `src/scenes/drops/`:

```
drops/
  index.tsx     # React-часть: сцена, клик, состояние переходов
  fragment.ts   # фрагментный шейдер (строка GLSL, частично генерируется)
  vertex.ts     # вершинный шейдер
  images.ts     # список картинок
  styles.css    # высота контейнера
```

## Идея эффекта

Прежде чем писать код, разберёмся, что именно мы считаем. Вся магия эффекта живёт в одной формуле:

```
radius = (uTime - t0) * speed
```

`t0` - момент, когда «упала капля», `uTime` - текущее время, `speed` - скорость расхождения. Для каждого пикселя мы считаем расстояние `d` до точки падения. Если `d < radius`, пиксель уже «охвачен кругом» и показывает новую картинку, иначе - старую. Всё остальное - украшения этой идеи:

1. Край круга делаем мягким (`smoothstep`).
2. Делаем край неровным, подмешивая шум к расстоянию.
3. Вдоль фронта пускаем волну, которая слегка смещает координаты текстуры (преломление) и подсвечивает фронт (блик).
4. Разрешаем нескольким каплям падать за один клик.
5. Разрешаем нескольким кликам идти одновременно: каждый клик - это отдельный «слой» со своей картинкой, а слои рисуются друг поверх друга от старого к новому.

Всё считается в фрагментном шейдере, то есть на видеокарте, для каждого пикселя независимо. JavaScript только хранит, где и когда упали капли, и отдаёт эти данные шейдеру.

## Шаг 1. Каркас: Canvas, камера и плоскость 16:9

Начнём с пустой сцены. Эффект двумерный, поэтому вся «сцена» - это одна плоскость, на которую натянута картинка.

```tsx
import { Canvas, useThree } from "@react-three/fiber";
import { PerspectiveCamera } from "@react-three/drei";

// плоскость имеет пропорции картинок (16:9)
const planeWidth = 16;
const planeHeight = 9;
const aspect = planeWidth / planeHeight;

const Drops = () => {
  const viewport = useThree((state) => state.viewport);

  // плоскость вписывается в окно
  const scale = Math.min(
    viewport.width / planeWidth,
    viewport.height / planeHeight,
  );

  return (
    <mesh scale={scale}>
      <planeGeometry args={[planeWidth, planeHeight]} />
      <meshBasicMaterial color="hotpink" />
    </mesh>
  );
};

export const DropsScene = () => (
  <div className="drops-canvas">
    <Canvas dpr={[1, 2]}>
      <color attach="background" args={["#000"]} />
      <PerspectiveCamera makeDefault fov={50} position={[0, 0, 10]} />
      <Drops />
    </Canvas>
  </div>
);
```

И стили, чтобы канвас растянулся на весь экран:

```css
.drops-canvas {
  height: 100vh;
}
```

Несколько решений, которые здесь принимаются, стоит проговорить.

**Плоскость 16 на 9, а не «полноэкранный квад».** Картинки у нас HD (1920x1080), то есть 16:9. Если сделать плоскость с такими же пропорциями, текстура ложится на неё без искажений и без обрезки: UV-координаты от 0 до 1 соответствуют краям картинки. Это сильно упрощает шейдер.

**`scale = min(...)`.** Это классический приём «вписать» (аналог `object-fit: contain`). Мы считаем, во сколько раз можно увеличить плоскость по ширине и по высоте окна, и берём меньшее из двух значений. Плоскость целиком помещается в окно, лишнее место заливается чёрным фоном. `viewport` из `useThree` даёт размер видимой области в единицах сцены на нулевой глубине (там, где стоит плоскость), поэтому формула работает при любом размере окна и любом `fov`.

**`dpr={[1, 2]}`.** Это диапазон плотности пикселей: не меньше 1 и не больше 2. Ретина-экран получит чёткую картинку, а на экранах с `devicePixelRatio = 3` мы не будем зря жарить видеокарту: стоимость фрагментного шейдера растёт пропорционально числу пикселей, а наш шейдер будет довольно тяжёлым.

**Камера на `z = 10` с `fov = 50`.** Значения подобраны так, чтобы плоскость 16x9 была удобно видна. Точные цифры не принципиальны, ведь масштаб мы всё равно вычисляем по `viewport`.

## Шаг 2. Загрузка текстур

Картинки лежат в отдельном файле, чтобы их список было легко менять:

```ts
// images.ts
// HD jpg links, any number of them (the server must send CORS headers)
export const images: string[] = [
  "https://picsum.photos/id/42/1920/1080.jpg",
  "https://picsum.photos/id/40/1920/1080.jpg",
  "https://picsum.photos/id/58/1920/1080.jpg",
  "https://picsum.photos/id/56/1920/1080.jpg",
];
```

Количество картинок не ограничено: мы будем ходить по ним по кругу. Единственное условие из комментария - сервер должен отдавать CORS-заголовки, иначе браузер не позволит использовать картинку как WebGL-текстуру (текстура с чужого домена без CORS «загрязняет» контекст, и WebGL отказывается её читать). `picsum.photos` заголовки отдаёт.

Загружаем всё одним вызовом `useTexture` из drei:

```tsx
import { useTexture } from "@react-three/drei";
import { Suspense } from "react";
import { SRGBColorSpace } from "three";

const textures = useTexture(images); // Texture[]

useMemo(() => {
  textures.forEach((texture) => {
    texture.colorSpace = SRGBColorSpace;
  });
}, [textures]);
```

и оборачиваем компонент в `Suspense`:

```tsx
<Suspense fallback={null}>
  <Drops />
</Suspense>
```

`useTexture` работает через React Suspense: пока картинки грузятся, компонент «приостанавливается», а `fallback={null}` просто ничего не рисует. Когда все четыре текстуры готовы, компонент рендерится с массивом готовых `Texture`.

**Про цветовое пространство.** Мы вручную ставим `colorSpace = SRGBColorSpace`, чтобы Three.js знал: в файле лежат цвета в sRGB, а не в линейном пространстве. Видеокарта при чтении текстуры переведёт их в линейные значения, шейдер будет считать смешивание в линейном пространстве, и в конце мы вернём цвета обратно в sRGB. Последний шаг делает строка `#include <encodings_fragment>` в конце шейдера - её мы увидим на шаге 3. Без неё и без правильного `colorSpace` картинка будет выглядеть блёклой или слишком тёмной.

## Шаг 3. Минимальный ShaderMaterial

Теперь заменим `meshBasicMaterial` на собственный шейдер. Сначала в самом простом виде: просто показать первую картинку.

Вершинный шейдер ([vertex.ts](../src/scenes/drops/vertex.ts)) - три строки смысла:

```glsl
varying vec2 vUv;

void main() {
  vUv = uv;
  gl_Position = projectionMatrix * modelViewMatrix * vec4(position, 1.0);
}
```

Что здесь происходит:

- `uv` - встроенный атрибут геометрии: координаты текстуры вершины, от (0, 0) в левом нижнем углу до (1, 1) в правом верхнем.
- `varying vec2 vUv` - переменная, которая передаётся из вершинного шейдера во фрагментный. Между вершинами она линейно интерполируется, поэтому в каждом пикселе плоскости мы получим «свои» UV. Именно по ним мы будем считать расстояние до капли.
- `projectionMatrix * modelViewMatrix * vec4(position, 1.0)` - стандартное преобразование позиции вершины в координаты экрана. Three.js сам подставляет эти матрицы в `ShaderMaterial`.

Фрагментный шейдер в первой версии:

```glsl
varying vec2 vUv;
uniform sampler2D uBase;

void main() {
  vec3 color = texture2D(uBase, vUv).rgb;
  gl_FragColor = vec4(color, 1.0);
  #include <encodings_fragment>
}
```

`uniform` - это значение, которое приходит в шейдер из JavaScript и одинаково для всех пикселей. `sampler2D` - тип текстуры. `texture2D(uBase, vUv)` читает цвет текстуры в точке `vUv`. Строка `#include <encodings_fragment>` - это директива Three.js, которая подставляет код преобразования цвета в выходное пространство (в sRGB).

В React-части материал выглядит так:

```tsx
const uniforms = useMemo(
  () => ({
    uBase: { value: textures[0] },
  }),
  // eslint-disable-next-line react-hooks/exhaustive-deps
  [],
);

<shaderMaterial
  uniforms={uniforms}
  vertexShader={vertex}
  fragmentShader={fragment}
/>
```

**Почему `useMemo` с пустым списком зависимостей.** `uniforms` - это объект, который `ShaderMaterial` хранит по ссылке, а мы потом будем менять `uniforms.uTime.value` каждый кадр. Если пересоздавать объект при каждом рендере, Three.js получит новый набор uniform-ов и значения, записанные в кадровом цикле, потеряются. Поэтому объект создаётся один раз и дальше только мутируется. Комментарий `eslint-disable` нужен потому, что линтер хочет видеть `textures` в зависимостях, а мы сознательно этого не делаем.

На этом шаге на экране уже должна быть первая картинка без эффектов.

## Шаг 4. Время, клик и первый круг

Чтобы «капля» росла, шейдеру нужно время. Заведём uniform `uTime` и будем обновлять его каждый кадр через `useFrame`:

```tsx
useFrame((state) => {
  uniforms.uTime.value = state.clock.elapsedTime;
});
```

`state.clock.elapsedTime` - секунды с момента старта канваса. Мы записываем его прямо в `uniforms`, минуя React-состояние: нам не нужен ре-рендер 60 раз в секунду, достаточно, чтобы шейдер видел свежее число.

Теперь клик. R3F позволяет вешать события прямо на меш, а в событии даёт `event.uv` - UV-координаты точки, в которую попал луч. Это ровно то, что нужно шейдеру:

```tsx
const onPointerDown = (event: ThreeEvent<PointerEvent>) => {
  if (!event.uv) return;
  event.stopPropagation();

  const time = uniforms.uTime.value as number;
  const { x, y } = event.uv;
  // дальше запишем (x, y, time) в uniform
};

<mesh scale={scale} onPointerDown={onPointerDown}>
```

`event.stopPropagation()` останавливает всплытие события к объектам позади: если на сцене появятся другие интерактивные меши, клик не «пробьёт» плоскость насквозь.

Сделаем первую, предельно простую версию шейдера: один круг, одна новая картинка.

```glsl
varying vec2 vUv;
uniform sampler2D uBase;
uniform sampler2D uNext;
uniform float uTime;
uniform float uSpeed;
// xy - место падения в uv, z - время падения
uniform vec3 uDrop;

void main() {
  float d = distance(vUv, uDrop.xy);
  float radius = max(uTime - uDrop.z, 0.0) * uSpeed;

  vec3 color = mix(
    texture2D(uBase, vUv).rgb,
    texture2D(uNext, vUv).rgb,
    step(d, radius)
  );

  gl_FragColor = vec4(color, 1.0);
  #include <encodings_fragment>
}
```

Разберём встроенные функции, которые нам пригодятся и дальше:

- `distance(a, b)` - расстояние между двумя точками.
- `step(edge, x)` возвращает 0.0, если `x < edge`, и 1.0 в противном случае. У нас `step(d, radius)` даёт 1.0 там, где `d <= radius`, то есть внутри круга.
- `mix(a, b, t)` - линейная интерполяция: `a * (1 - t) + b * t`. При `t = 0` получаем `a`, при `t = 1` получаем `b`. Это главный инструмент любых переходов.
- `max(uTime - uDrop.z, 0.0)` - до момента падения радиус не должен быть отрицательным.

Если запустить такую версию, мы увидим расширяющийся круг с жёстким краем. Только круг этот будет... овальным.

## Шаг 5. Коррекция пропорций

Овал получается потому, что UV всегда лежат в квадрате 1x1, а на экране плоскость растянута до 16:9. Расстояние 0.1 по горизонтали - это 1.6 единицы в сцене, а расстояние 0.1 по вертикали - всего 0.9. Круг в UV-пространстве превращается в эллипс на экране.

Лечится это умножением горизонтальной составляющей на соотношение сторон:

```glsl
uniform float uAspect;

vec2 delta = (vUv - uDrop.xy) * vec2(uAspect, 1.0);
float d = length(delta);
```

Теперь `x` измеряется в единицах «ширины в высотах», а `y` - в высотах, то есть мы работаем в пространстве, где один шаг по любой оси выглядит одинаково. В React-коде `uAspect` - просто константа `planeWidth / planeHeight`:

```tsx
uAspect: { value: aspect },
```

Побочное следствие, которое пригодится на шаге с длительностью: радиус теперь измеряется в «высотах плоскости», а не в долях ширины. Максимальное расстояние от точки на плоскости до самого дальнего угла равно диагонали, то есть `hypot(aspect, 1)`, это около 2.04.

Вместо `distance` мы теперь явно считаем `delta` - вектор от капли до пикселя. Он нам понадобится ещё раз для направления преломления.

## Шаг 6. Мягкий край

Жёсткий `step` даёт неприятную «пиксельную» кромку. Заменим его на `smoothstep`:

```glsl
uniform float uEdge;

float reveal = 1.0 - smoothstep(radius - uEdge, radius, d);
```

`smoothstep(a, b, x)` возвращает 0.0, если `x <= a`, 1.0, если `x >= b`, и плавно (по S-образной кривой) переходит между ними. Мы инвертируем результат: внутри круга на глубину `uEdge` значение равно 1, на фронте оно плавно падает до 0, а снаружи равно 0.

Таким образом, `uEdge` - это ширина размытой кромки в тех же «высотах плоскости». При значении по умолчанию `0.06` это около шести процентов высоты картинки: достаточно, чтобы край выглядел мягким, но всё ещё читался как граница.

Обратите внимание: размытие идёт **внутрь** круга (от `radius - uEdge` до `radius`), а не наружу. Благодаря этому полностью «закрытый» радиус гарантированно не выходит за `radius`, и это упрощает расчёт длительности перехода (шаг 12).

## Шаг 7. Неровный край: value noise

Идеальная окружность выглядит как циркульный чертёж, а не как капля. Чтобы край стал живым, будем слегка «шевелить» расстояние шумом: в одних местах круг выпирает, в других - отстаёт.

В GLSL нет встроенного шума, но его можно сделать в десяток строк. Нам нужны две функции.

Первая - дешёвая псевдослучайная функция: по двумерной точке возвращает число от 0 до 1.

```glsl
float hash(vec2 p) {
  return fract(sin(dot(p, vec2(127.1, 311.7))) * 43758.5453);
}
```

Это классический «хак»: скалярное произведение сворачивает точку в одно число, `sin` перемешивает, огромный множитель раздувает разницу между соседними значениями, а `fract` оставляет дробную часть. Это не настоящий генератор случайных чисел, но для визуального шума его более чем достаточно.

Вторая - value noise: случайные значения в узлах целочисленной решётки с гладкой интерполяцией между ними.

```glsl
float noise(vec2 p) {
  vec2 i = floor(p);
  vec2 f = fract(p);
  f = f * f * (3.0 - 2.0 * f);
  return mix(
    mix(hash(i), hash(i + vec2(1.0, 0.0)), f.x),
    mix(hash(i + vec2(0.0, 1.0)), hash(i + vec2(1.0, 1.0)), f.x),
    f.y
  );
}
```

Как это работает:

- `floor(p)` - индекс клетки решётки, `fract(p)` - позиция внутри клетки (от 0 до 1).
- В четырёх углах клетки берём случайные значения из `hash`.
- Билинейно смешиваем их: сначала по `x` на верхней и нижней сторонах, потом по `y` между результатами.
- Строка `f = f * f * (3.0 - 2.0 * f)` - это та же S-кривая, что и в `smoothstep`. Без неё на границах клеток были бы видны изломы (интерполяция линейна, и производная скачет); с ней шум получается гладким.

Один слой шума выглядит слишком «ровным», поэтому берём два с разным масштабом (октавы) и складываем с весами:

```glsl
float n = noise(uv * uNoiseScale) * 0.65 + noise(uv * uNoiseScale * 2.3) * 0.35;
```

Вторая октава в 2.3 раза мельче и вносит в форму край мелких неровностей на фоне крупных. Веса 0.65 и 0.35 в сумме дают 1, поэтому `n` остаётся в диапазоне от 0 до 1. Почему именно 2.3, а не 2? Если брать ровно 2, решётки октав совпадают по узлам, и шум становится заметно регулярным; иррациональный множитель разрушает это совпадение.

Теперь применяем шум к расстоянию:

```glsl
float front = d + (n - 0.5) * 2.0 * uNoiseAmount;
float reveal = 1.0 - smoothstep(radius - uEdge, radius, front);
```

`(n - 0.5) * 2.0` переводит шум из диапазона [0, 1] в [-1, 1]. Умножив на `uNoiseAmount` (по умолчанию `0.1`), получаем сдвиг расстояния до плюс-минус десяти процентов высоты картинки. Там, где шум положительный, пиксель «кажется» дальше от капли, и круг до него добирается позже. Где отрицательный - ближе, и круг его захватывает раньше. Параметр `uNoiseScale` (по умолчанию `3.5`) задаёт частоту: чем он выше, тем мельче «пятна» шума.

Заметьте два свойства этого приёма:

1. Шум зависит только от координат пикселя, а не от времени. Поэтому форма неровностей неподвижна, а растёт только радиус. Выглядит как граница, которая растекается по «неоднородной поверхности». Это не баг: тот же шум делает рисунок кромки одинаковым для всех капель.
2. Шум считается по сырым `uv`, а не по скорректированным на пропорции. Из-за этого пятна шума вытянуты по горизонтали на те же 16/9. На практике незаметно, но если нужна изотропия, умножьте аргумент на `vec2(uAspect, 1.0)`.

## Шаг 8. Волна на фронте: преломление и блик

Сейчас эффект выглядит как плавная «маска». Чтобы он стал похож на воду, добавим на фронте волну. Она делает две вещи: слегка смещает координаты текстуры (как будто картинка видна через неровную линзу) и подсвечивает гребни.

Положение пикселя относительно фронта:

```glsl
float x = front - radius;
```

Если `x > 0`, пиксель ещё впереди фронта, если `x < 0` - уже позади. Волна - это синусоида по `x`, которую мы умножаем на огибающую (envelope), чтобы она жила только рядом с фронтом:

```glsl
float envelope = x > 0.0 ? exp(-x * x * 400.0) : exp(x * 4.0);
float fade = 1.0 - smoothstep(0.0, 2.2, radius);
float wave = sin(x * uWaveFrequency) * envelope * fade;
```

- Впереди фронта огибающая - `exp(-x*x*400)`, то есть гауссиана: ширина около 0.05, и за пределами этого узкого «предвестника» волны нет. Он резкий.
- Позади фронта - `exp(x*4)` при отрицательном `x`: экспоненциальный спад, который тянет за кругом затухающий «шлейф» в несколько десятых высоты.
- Асимметрия - ключевой приём. Симметричная волна выглядела бы как кольцо, а асимметричная («резко впереди, шлейф позади») похожа на рябь от падения.
- `fade` гасит волну по мере роста радиуса: от 1.0 в начале до 0 при радиусе 2.2. Это чуть больше диагонали плоскости, поэтому к концу перехода рябь полностью исчезает, и последний кадр совпадает с чистой картинкой.
- `uWaveFrequency` (по умолчанию `28`) - пространственная частота: длина волны около `2π / 28`, то есть примерно 0.22 высоты.

Теперь используем `wave` двумя способами.

**Преломление.** Смещаем координаты, по которым читается текстура, вдоль направления от капли:

```glsl
offset += normalize(delta + 1e-5) * wave * uWaveAmount;
// ...
vec3 color = texture2D(uBase, uv + offset).rgb;
```

`normalize(delta)` - единичный вектор «от капли к пикселю». Умножаем на `wave * uWaveAmount` (по умолчанию `0.01`, то есть сдвиг до одного процента картинки), и в разных местах фронта картинка то «набегает», то «отбегает». Добавка `1e-5` защищает от деления на ноль: ровно в центре капли `delta = (0, 0)`, а `normalize` нулевого вектора даёт `NaN`, который превращается в чёрный пиксель.

**Блик.** Суммируем значения волны и добавляем к цвету:

```glsl
light += wave;
// ...
color += light * uLight;
```

`uLight` по умолчанию совсем маленький, `0.01`: этого достаточно, чтобы гребни волны чуть светлели, а впадины чуть темнели, и это придаёт воде объём. Увеличьте параметр до `0.1` и получите стеклянный блеск.

Важно, что `offset` применяется ко всем текстурам (и к базовой, и ко всем слоям) одинаково. Это даёт ощущение, что рябь лежит поверх всего изображения, а не только поверх одной картинки.

## Шаг 9. Несколько капель на клик

Одна капля выглядит скучновато. Пусть за один клик падает от 1 до 8 капель с паузой между ними, и каждая следующая падает рядом с предыдущими.

В шейдере капли хранятся массивом `vec3` (x, y, время падения), а обработка превращается в цикл:

```glsl
uniform vec3 uDrops[DROPS];

float reveal = 0.0;
for (int i = 0; i < DROPS; i++) {
  vec3 drop = uDrops[i];
  // ... считаем delta, d, radius, front, wave для этой капли
  if (fallen) {
    reveal = max(reveal, 1.0 - smoothstep(radius - uEdge, radius, front));
  }
  offset += normalize(delta + 1e-5) * wave * uWaveAmount;
  light += wave;
}
```

Три момента, на которые стоит обратить внимание.

**`max` для маски.** Если несколько кругов перекрываются, пиксель должен считаться «открытым», как только его достиг любой из них. Объединение масок - это максимум. Волны же складываются: пересечение двух рябей даёт интерференцию.

**`fallen = uTime > drop.z`.** Капли в одном клике падают с задержкой `dropDelay` (по умолчанию `0.25` с). До своего момента капля не должна влиять ни на маску, ни на волну.

**Размер массива - константа.** В GLSL размер массива и границы цикла должны быть известны на этапе компиляции. Поэтому в шейдере написано `DROPS`, а значение приходит из JavaScript через `defines` материала:

```tsx
<shaderMaterial defines={{ DROPS: maxDrops, LAYERS: maxLayers }} ... />
```

`defines` превращается в `#define DROPS 8` в начале шейдера. Сколько капель реально упало, регулируется не размером массива, а временем: лишние слоты просто заполнены «ещё не упавшими» каплями.

Теперь о стороне JavaScript. Параметры клика - `dropsCount` (по умолчанию `1`, максимум `8`), `dropSpread` (`0.07`) и `dropDelay` (`0.25`):

```tsx
const { speed } = settingsRef.current;
for (let i = 0; i < dropsCount; i++) {
  // первая капля падает ровно туда, где клик; следующие - за фронтом предыдущих
  const distance =
    i === 0
      ? 0
      : speed * dropDelay * i + dropSpread * (0.5 + Math.random() / 2);
  const angle = Math.random() * Math.PI * 2;
  drops[i * 3] = MathUtils.clamp(x + (Math.cos(angle) * distance) / aspect, 0, 1);
  drops[i * 3 + 1] = MathUtils.clamp(y + Math.sin(angle) * distance, 0, 1);
  drops[i * 3 + 2] = time + i * dropDelay;
}
```

**Почему не просто случайный разброс вокруг клика.** Первая версия сдвигала каждую каплю на случайную величину из `[-spread, +spread]`. На практике выходило, что число капель на экране не менялось: пока падает вторая капля (через `dropDelay`), первая уже разошлась на `speed * dropDelay` (при настройках по умолчанию это 0.2 высоты плоскости). Если вторая упала ближе этого расстояния, её круг целиком лежит внутри уже проявленной области и не добавляет ничего, кроме волны. Новая картинка показывается там, где круг выходит за границу предыдущих, поэтому капли нужно ставить за их фронтом.

- Расстояние `distance` считается в высотах плоскости. Первое слагаемое `speed * dropDelay * i` - то, как далеко успели разойтись предыдущие капли к моменту падения `i`-й, и туда ставить бесполезно. Второе, `dropSpread * (0.5 + random / 2)`, - запас за этим фронтом: от половины до целого `dropSpread`. Поэтому новый круг гарантированно виден, а `dropSpread` регулирует, насколько он выступает.
- Угол выбирается случайно. Для перевода в uv смещение по `x` делится на `aspect`: расстояние измерено в высотах, а ось `x` в uv растянута на ширину.
- Первая капля падает строго в точку клика, потому что человек ожидает увидеть реакцию именно там, куда нажал.
- `MathUtils.clamp(..., 0, 1)` не даёт каплям упасть за пределы плоскости.
- Время падения `time + i * dropDelay` растёт с индексом: капли идут «каскадом».

## Шаг 10. Слои: несколько кликов одновременно

Пока наша сцена умеет только один переход за раз. Если кликнуть во время перехода, нужно либо игнорировать клик (скучно), либо начать новый, не прерывая старый. Мы выберем второй вариант, и тут нужна идея слоёв.

Представим стопку прозрачных плёнок. Внизу лежит базовая картинка (`uBase`), поверх неё - картинки от текущих переходов, каждая со своей маской. Старый переход ниже, новый выше. Это и есть цикл по слоям:

```glsl
vec3 color = texture2D(uBase, uv + offset).rgb;
color = mix(color, texture2D(uLayer0, uv + offset).rgb, reveals[0]);
color = mix(color, texture2D(uLayer1, uv + offset).rgb, reveals[1]);
// ... и так для каждого слоя
```

Каждый `mix` поверх предыдущего результата работает как наложение с прозрачностью: `reveals[k]` - это маска слоя `k`, посчитанная на шаге 9. Если слой не используется, его маска равна нулю, и `mix` ничего не меняет.

**Почему нельзя написать цикл?** Естественно было бы написать `for (int k...) color = mix(color, texture2D(uLayers[k], ...), reveals[k])`, но в WebGL к массиву сэмплеров нельзя обращаться по изменяемому индексу: допустим только константный индекс. Поэтому мы генерируем код **из JavaScript**, на этапе сборки строки шейдера ([fragment.ts](../src/scenes/drops/fragment.ts)):

```ts
export const maxDrops = 8;
export const maxLayers = 6;

const layerSamplers = Array.from(
  { length: maxLayers },
  (_, k) => `uniform sampler2D uLayer${k};`,
).join("\n");

const layerMix = Array.from(
  { length: maxLayers },
  (_, k) =>
    `color = mix(color, texture2D(uLayer${k}, uv + offset).rgb, reveals[${k}]);`,
).join("\n  ");
```

Эти строки подставляются в шаблон через `${layerSamplers}` и `${layerMix}`. Получается «развёрнутый цикл», сгенерированный для заданного `maxLayers`. Хочется шесть слоёв - меняем одну константу, шейдер перестроится сам. Это распространённый приём: когда язык не умеет чего-то динамически, мы делаем это на уровне метапрограммирования.

Заметьте, что `reveals` - это массив `float reveals[LAYERS]`, а не отдельные переменные. Индексы здесь константные (в сгенерированных строках `reveals[0]`, `reveals[1]`), а в основном цикле `reveals[k]` пишется по изменяемому индексу, но массив `float` (не сэмплеров) индексировать так можно.

Вложенный цикл по слоям и каплям выглядит так:

```glsl
for (int k = 0; k < LAYERS; k++) {
  reveals[k] = 0.0;
  for (int i = 0; i < DROPS; i++) {
    vec3 drop = uDrops[k * DROPS + i];
    // ...
    reveals[k] = max(reveals[k], 1.0 - smoothstep(radius - uEdge, radius, front));
  }
}
```

Массив `uDrops` теперь содержит `LAYERS * DROPS` троек подряд: сначала все капли слоя 0, затем слоя 1 и так далее. Индекс капли - `k * DROPS + i`.

## Шаг 11. Как передать капли в шейдер

Здесь есть пара нетривиальных решений. Массив `uDrops` объявлен как `uniform vec3 uDrops[LAYERS * DROPS]`, то есть 6 x 8 = 48 векторов. В JavaScript можно было бы передать массив `Vector3`, но мы используем плоский `Float32Array`:

```tsx
// the drops of all layers in a row; a flat array, not Vector3, so that
// three uploads it as is
uDrops: { value: new Float32Array(maxLayers * maxDrops * 3) },
```

Для векторных массивов Three.js умеет принимать как массив объектов, так и «плоский» набор чисел. Плоский типизированный массив уходит в видеокарту как есть, без промежуточного копирования и без аллокации объектов, а мы будем перезаписывать его каждый кадр.

Каждый кадр мы заполняем массив данными слоёв:

```tsx
const drops = uniforms.uDrops.value as Float32Array;
for (let k = 0; k < maxLayers; k++) {
  const layer = layers.current[k];
  uniforms[`uLayer${k}`].value = layer
    ? layer.texture
    : uniforms.uBase.value;
  const offset = k * maxDrops * 3;
  for (let i = 0; i < maxDrops * 3; i++) {
    // a slot that is not used: its drops have not fallen yet
    drops[offset + i] = layer ? layer.drops[i] : i % 3 === 2 ? idle : 0.5;
  }
}
```

Что здесь важно:

- **Слот без слоя.** Для пустого слота текстура берётся базовая (чтобы всегда была корректная привязка текстуры, ведь пустой сэмплер недопустим), а капли заполняются «заглушками».
- **`idle = 1e9`.** Заглушка для времени падения - гигантское число, которое «наступит» через тридцать лет. Для шейдера это капля, которая ещё не упала: `fallen = uTime > 1e9` ложно, радиус равен нулю, воздействия нет. Благодаря этому не нужно передавать «количество активных капель»: неиспользуемые слоты сами себя отключают.
- **Координаты по умолчанию `0.5`.** Просто безопасное значение внутри диапазона, чтобы не получить странных чисел на неиспользуемых тройках.
- **Склейка по `i % 3 === 2`.** Каждая третья ячейка плоского массива - это компонента `z` (время). Остальные - `x` и `y`.

Каждый кадр мы переписываем 144 числа (`6 * 8 * 3`). Это ничтожно мало, и ради простоты кода не нужны никакие «флаги изменения».

**Ограничения.** 48 `vec3`-uniform'ов умещаются в лимиты практически любого GPU, включая мобильные (WebGL2 гарантирует минимум 224 вектора во фрагментном шейдере, а реальные устройства дают заметно больше), но если вы поднимете `maxLayers` или `maxDrops` до очень больших значений, придётся задуматься о текстуре данных вместо uniform-массива.

## Шаг 12. Жизненный цикл перехода

Теперь соберём логику клика и очереди слоёв. Состояние переходов хранится в `useRef`, а не в `useState`:

```tsx
// a transition that is running: the image comes out of the drops of one click
type TLayer = {
  texture: Texture;
  // x, y, time of every drop in a row
  drops: Float32Array;
  endsAt: number;
};

const nextImage = useRef(0);
// running transitions, the oldest first; each is drawn over the previous
const layers = useRef<TLayer[]>([]);
```

Состояние постоянно меняется (слои добавляются при клике и убираются по таймеру), но интерфейсу React это не нужно знать: рисует всё шейдер, и ему данные доставляются через uniform. Ref не вызывает ре-рендер, значит, не будет лишней работы на каждый клик.

Клик создаёт слой:

```tsx
const onPointerDown = (event: ThreeEvent<PointerEvent>) => {
  // all the slots are busy, wait for the oldest transition to end
  if (layers.current.length >= maxLayers || !event.uv) {
    return;
  }
  event.stopPropagation();

  const time = uniforms.uTime.value as number;
  const { x, y } = event.uv;
  const { dropsCount, dropSpread, dropDelay } = settingsRef.current;

  nextImage.current = (nextImage.current + 1) % textures.length;
  const drops = Float32Array.from({ length: maxDrops * 3 }, (_, i) =>
    i % 3 === 2 ? idle : 0.5,
  );
  // ... заполняем первые dropsCount капель (шаг 9)

  layers.current.push({
    texture: textures[nextImage.current],
    drops,
    endsAt: time + duration,
  });
};
```

- Если все шесть слотов заняты, клик молча игнорируется: следующий переход можно начать, как только освободится самый старый.
- `nextImage` циклически перебирает картинки через `% textures.length`. Первая картинка (индекс 0) показана в начале, поэтому первый клик покажет вторую.
- Новый слой кладётся в конец очереди: так он оказывается сверху в стопке.

**Сколько длится переход?** Нужно знать момент, когда слой полностью проявился и его можно «слить» с базой. Рассуждение такое: самая дальняя точка плоскости от точки падения находится не дальше диагонали, и это `hypot(aspect, 1)`, около 2.04 (капли обрезаны `clamp`'ом внутри плоскости, поэтому дальше диагонали не уйти). Фронт должен не просто достичь этой точки, но и выйти за неё вместе с мягким краем (`edge`) и с учётом сдвига от шума (`noiseAmount`). Это путь, который делится на скорость. К нему прибавляется задержка последней капли:

```tsx
const duration =
  (Math.hypot(aspect, 1) + s.edge + s.noiseAmount) / s.speed +
  s.dropDelay * (s.dropsCount - 1);
```

С настройками по умолчанию (`edge = 0.06`, `noiseAmount = 0.1`, `speed = 0.8`, одна капля) это `(2.04 + 0.06 + 0.1) / 0.8 = 2.75` секунды.

А каждый кадр мы проверяем, не закончился ли самый старый слой:

```tsx
// a transition that has fully come out: its image becomes the base
while (layers.current.length && time >= layers.current[0].endsAt) {
  uniforms.uBase.value = layers.current.shift()!.texture;
}
```

Когда слой закончился, его картинка уже полностью заменила всё, что было под ней. Поэтому её можно объявить новой базой, а слой удалить из очереди. Слои сдвигаются на позицию вниз, и картинка на экране не меняется: переход выглядит непрерывным. `while`, а не `if`, потому что за один кадр (например, при возвращении на вкладку после паузы) может закончиться сразу несколько слоёв.

## Шаг 13. Панель настроек на leva

Все числа эффекта вынесены в панель `leva`. Это не просто удобство для отладки: эффект - вещь «на глаз», и ползунки позволяют подобрать характер воды за пять минут.

```tsx
const settings = useControls("drops", {
  dropsCount: { value: 1, min: 1, max: maxDrops, step: 1 },
  // how far beyond the front of the earlier drops the next one falls (in
  // heights of the plane); a drop inside an earlier circle would be invisible
  dropSpread: { value: 0.07, min: 0, max: 0.5, step: 0.01 },
  // pause between the drops of one click, seconds
  dropDelay: { value: 0.25, min: 0, max: 1, step: 0.01 },
  // speed of the front, in heights of the plane per second
  speed: { value: 0.8, min: 0.1, max: 3, step: 0.05 },
  // softness of the edge of the new image
  edge: { value: 0.06, min: 0.005, max: 0.5, step: 0.005 },
  // how far the noise pushes the edge of a circle
  noiseAmount: { value: 0.1, min: 0, max: 0.5, step: 0.005 },
  // size of the details of the edge, higher = smaller
  noiseScale: { value: 3.5, min: 1, max: 30, step: 0.5 },
  waveAmount: { value: 0.01, min: 0, max: 0.05, step: 0.001 },
  waveFrequency: { value: 28, min: 5, max: 150, step: 1 },
  light: { value: 0.01, min: 0, max: 0.3, step: 0.005 },
});
```

Сводная таблица:

| Параметр | По умолчанию | Диапазон | Что делает |
| --- | --- | --- | --- |
| `dropsCount` | 1 | 1..8 | сколько капель падает за клик |
| `dropSpread` | 0.07 | 0..0.5 | насколько дальше фронта предыдущих капель падает следующая (в высотах плоскости) |
| `dropDelay` | 0.25 | 0..1 | пауза между каплями, секунды |
| `speed` | 0.8 | 0.1..3 | скорость фронта, высот плоскости в секунду |
| `edge` | 0.06 | 0.005..0.5 | мягкость кромки |
| `noiseAmount` | 0.1 | 0..0.5 | насколько шум сдвигает край |
| `noiseScale` | 3.5 | 1..30 | размер деталей края (больше - мельче) |
| `waveAmount` | 0.01 | 0..0.05 | сила преломления |
| `waveFrequency` | 28 | 5..150 | частота волны на фронте |
| `light` | 0.01 | 0..0.3 | сила блика |

Значения из панели мы передаём в шейдер внутри `useFrame`:

```tsx
const s = settingsRef.current;
uniforms.uSpeed.value = s.speed;
uniforms.uEdge.value = s.edge;
uniforms.uNoiseAmount.value = s.noiseAmount;
uniforms.uNoiseScale.value = s.noiseScale;
uniforms.uWaveAmount.value = s.waveAmount;
uniforms.uWaveFrequency.value = s.waveFrequency;
uniforms.uLight.value = s.light;
```

**Зачем нужен `settingsRef`.** Вспомните, что `useControls` возвращает новый объект при каждом изменении ползунка. Обработчик клика и колбэк `useFrame` создаются в замыканиях, которые могут «застрять» на значениях предыдущего рендера. Чтобы всегда читать актуальные настройки, мы кладём их в ref:

```tsx
// the handlers below live in the closure of the first render
const settingsRef = useRef(settings);
settingsRef.current = settings;
```

Теперь любой обработчик читает `settingsRef.current` и гарантированно видит свежие значения, вне зависимости от того, как часто и когда перепривязываются колбэки. Это стандартный паттерн «ref на последнюю версию».

**Важный нюанс про параметры, которые нельзя менять на лету.** `speed`, `edge` и `noiseAmount` участвуют не только в шейдере, но и в расчёте длительности `endsAt` в момент клика. Если изменить `speed` посреди перехода, шейдер начнёт считать радиус по-новому, а `endsAt` останется старым. Слой может закончиться раньше, чем фронт дойдёт до края, и на экране появится скачок. Для отладочной панели это терпимо, но в продакшене параметры лучше фиксировать на момент клика и хранить внутри слоя.

## Подводные камни

Несколько мест, на которых легко споткнуться.

**Стоимость шейдера.** На каждый пиксель мы выполняем `LAYERS * DROPS` итераций (48) с `sqrt`, `exp`, `sin` и `normalize`, плюс 7 чтений текстур (база и 6 слоёв) и два вызова шума. На современных видеокартах это нормально, на слабых мобильных вы увидите просадку частоты кадров. Рычаги: уменьшить `maxLayers` и `maxDrops`, понизить верхнюю границу `dpr`, а в самом шейдере пропускать слой, у которого нет упавших капель.

**Циклы с константными границами.** `for (int k = 0; k < LAYERS; k++)` компилируется только потому, что `LAYERS` - константа через `defines`. Попытка сделать границу из uniform-переменной приведёт к ошибке компиляции в WebGL1.

**Неиспользуемые слоты должны быть безопасными.** Если пустой слот оставить с нулями, то «время падения 0» значит «капля упала в начале времён» и маска залита целиком. Поэтому нужны `idle = 1e9`, а не `0`.

**CORS.** Картинка без заголовка `Access-Control-Allow-Origin` загрузится в `<img>`, но использовать её как текстуру не получится: консоль браузера покажет ошибку безопасности. Проверяйте заголовки у своих источников.

**Цветовое пространство.** Если картинки на экране тусклее или темнее оригинала, проверьте две вещи: `texture.colorSpace = SRGBColorSpace` и наличие `#include <encodings_fragment>` в конце шейдера. Нужны оба условия вместе.

**Переименование include между версиями Three.js.** В проекте используется `three` 0.153, где этот include называется `encodings_fragment`. В более новых версиях он заменён на `colorspace_fragment`, так что после обновления библиотеки шейдер придётся поправить - заглядывайте в changelog.

## Куда развивать

- **Нормали вместо смещения вдоль радиуса.** Сейчас преломление смещает UV вдоль направления от капли. Можно считать нормаль поверхности воды из градиента волны и вычислять смещение по закону преломления, получится более убедительное «стекло».
- **Рендер в текстуру вместо слоёв.** Подход с `uLayerN` прост, но ограничен числом сэмплеров. Если нужно больше одновременных переходов, можно рисовать результат в `RenderTarget` и использовать его в качестве базы (ping-pong), тогда слои не будут накапливаться.
- **Свои картинки.** Достаточно изменить `images.ts`, но помните про соотношение сторон: плоскость захардкожена как 16:9. Для других пропорций поменяйте `planeWidth` и `planeHeight`, шейдер подхватит `uAspect` сам.
- **Тач и клавиатура.** `onPointerDown` уже работает и с тачскрином. Запуск перехода по стрелкам или таймеру - это вызов той же функции создания слоя без `event.uv`.
- **Звук.** Каждая капля - готовый триггер для звука с задержкой `dropDelay`.

## Итоги

Мы собрали эффект перехода «каплями» из простых кирпичиков:

1. Радиус растёт со временем, расстояние до капли делит плоскость на «до» и «после».
2. Пропорции экрана корректируются умножением `x` на `aspect`, иначе круг становится овалом.
3. `smoothstep` делает край мягким, value noise из двух октав делает его живым.
4. Асимметричная волна (резкая впереди, затухающая позади) даёт преломление и блик.
5. Несколько капель и несколько слоёв - это циклы в шейдере, где неиспользуемые элементы отключаются временем `1e9`, а не отдельными флагами.
6. Ограничения GLSL (константные границы циклов и индексы сэмплеров) обходятся через `defines` и генерацию кода из JavaScript.
7. Состояние переходов живёт в `ref`, данные летят в шейдер через мутацию uniform'ов в `useFrame`, и React ничего не перерисовывает.

Сцена зарегистрирована в приложении под адресом `/drops` ([App.tsx](../src/App.tsx)). Откройте её, покрутите ползунки в панели и посмотрите, как каждый параметр меняет характер воды: лучше всего приём понимается руками.
